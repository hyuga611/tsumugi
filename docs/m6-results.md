# m6-results — シェル統合の配布と、編集の差分化

M6 で入れたもの、実機で確かめた結果、そこで見つけて直したバグ。

---

## 1. シェル統合を配る（これが無いと製品の中核語彙が全部死ぬ）

`[[` `]]` `[e` `]e`、左ガターのマーカー、`ac` / `io`（コマンドブロック）は
**すべて OSC 133 から「プロンプトがどこか」を得ている**。素の cmd.exe で使うと、
端末としては動くのに tsumugi である意味がほとんど無い。M0 で「ConPTY を OSC 133 が通る」
ことは確かめてあったが、**それを出すシェル側の設定を配っていなかった**。

`shell-integration/` に bash / zsh / fish / PowerShell / nushell 向けを置き、
バイナリへ埋め込んだ。

```
tsg --install-shell-integration        # 今のシェルを見て置き、rc に 1 行足す
tsg --shell-integration bash           # 中身を標準出力へ（eval で読ませる）
```

- **埋め込む**のは、exe を 1 つ置いただけの環境で最初の 1 回を走らせたいから。
  別ファイルを探しに行く形だと、そこで何も出せない。
- **rc への追記はべき等**。すでに入っていれば触らない（毎回追記して rc が太るより、
  何度走らせても同じ状態になることを取った）。
- `tsumugi.ps1` だけ**コメントも含めて ASCII**。Windows PowerShell 5.1 は BOM 無しの
  `.ps1` を ANSI コードページとして読むので、日本語コメントが CP932 の 2 バイト目に
  バッククォートや引用符を持ち込んで**構文を壊す**ことがある。
  パイプ（`| Invoke-Expression`）経由では BOM も付けられないので、ASCII に保つのが唯一確実。
  テストで固定してある（`the_powershell_script_stays_ascii`）。
- cmd.exe には同じ口が無い。ヘルプにそう書いた。

### 実機で確かめたこと

PowerShell で読み込んで `echo` を 2 回、`cmd /c exit 3`、`echo` を 1 回:

- 左ガターに**細い緑 3 本と太い赤 1 本**が出た（成功と失敗が見分けられている）
- `]e` で失敗したコマンドへ飛べた
- `vac` で `PS C:\Users\atlan\dev\tsumugi> cmd /c exit 3` がクリップボードへ入った
- `Space v` で割った新しいペインが**同じディレクトリで開いた**（OSC 7 が届いている。
  統合前はホームで開いていた）

## 2. 編集を差分で送る

打鍵ごとに全文を socket へ流していた。取り消しも全文スナップショットを積んでいた。
どちらも大きなファイルで効いてくる。

**やり方**: 変更の前後の全文を比べ、前後の共通部分を落として 1 つの置換
（`Splice { start, removed, inserted }`）にまとめる。

なぜ「経路ごとに逆操作を書く」ではなくこうしたか:

> 文字単位・行単位・矩形で逆操作の形が変わる。境界の扱いを 1 つ間違えると
> 「取り消したら壊れた」が起きる。差分を取る形なら**変更の種類が何であっても
> 出てくる形は 1 つ**で、取り消しにもサーバへの送信にも同じものを使える。

- プロトコル版 7。`EditFile { pane, base_len, edits }` が普段の経路。
- `base_len` はクライアントが思っているサーバ側の長さ。食い違ったらサーバは
  **当てずに** `NeedFullFile` を返し、クライアントが全文を送り直す。
  ずれたまま当てると中身が静かに壊れる。文字境界も受け側で確かめる（外すと `String` が壊れて落ちる）。
- 取り消し / やり直しの後だけは全文を渡し直す。何段でも一度に動くので、
  位置つきの差分へ落とすより確実で、頻度が低いので実害も無い。

数字（テストで固定）:

| | 前 | 後 |
|---|---|---|
| 1 打鍵で送る量 | ファイル長 | 数バイト |
| 取り消し 1 段の記録 | ファイル長 | 変更したぶん |
| 100KB のファイルで戻れる段数 | 40 段ほど（4MB の上限） | 上限の 500 段 |

## 3. 実機で見つけたバグ（3 件）

すべて「テストは通っているのに、実際に打つと違うものが出る」型。

### 3.1 エディタで `i` を押すとシェルのカーソル行へ飛ぶ

入力モードへ入るたびに `snap_to_live_tail()` を呼んでいた。ファイルを開いている
ペインには「生きた末尾」が無いのに、**下で走っているシェルのカーソル位置**へ
カーソルを飛ばしていた。ファイルの 1 行目を編集したつもりが 3 行目の途中に入る。

### 3.2 行末に打つと文字の順序が入れ替わる

`alpha` の行末に `-EDIT` と打つと `alphaEDIT-` になった。

通常モードのカーソルは「文字の上」に居るので最後の文字までしか行けない。
入力モードのカーソルは「文字と文字の間」に居るので、行末の**1 つ先**が要る。
同じ `clamp` を使い回していたため、1 文字打った直後にカーソルが引き戻され、
次の文字がその手前へ入っていた。`clamp_insert` を分けた。

### 3.3 `A` `I` `o` `O` が `i` と同じだった

端末では正しい（打てるのは生きたプロンプトだけなので位置を選ぶ意味が無い）が、
ファイルでは vim と同じに振る舞うべきだった。`InsertAt` を足して、
**バッファの種別で振る舞いを変える**形にした。

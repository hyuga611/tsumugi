# concept — 何を捨て、何を取るか

> tsumugi（紡ぎ）/ バイナリ `tsg` — 名前は仮。
> 対象: クロスプラットフォーム（Windows / macOS / Linux）。実装言語 Rust。

---

## 一行で

**ターミナルの画面そのものを、vim で編集できるドキュメントとして扱う。そしてその全操作にマウスの道を用意する。**

---

## 出発点の観察

既存のターミナルは、画面を「書き込み専用のログ」として持っている。あとから中身を触るための
機能は、すべて**飛び地**として後付けされた。

- WezTerm / Kitty の copy-mode は vim 風だが、入るのに専用キーが要り、抜けると消える一時状態。
  マウスは基本的に使えない。
- スクロールバックは「見るもの」であって「触るもの」ではない。行を消す・整形する・
  一部だけ別プロセスに流す、といった操作の語彙が無い。
- 編集したくなったら外部の nvim を起動する。するとターミナルの中でターミナルが動き、
  キーもマウスも二重に解釈され、コピーもスクロールも別世界になる。
- マウス派は copy-mode の恩恵をほぼ受けられない。キーボード派は右クリックメニューを軽蔑する。
  **どのターミナルも、この2派を1つの機能セットで満たしていない。**

Neovim は逆の穴を持つ。バッファは完全に「触れるドキュメント」だが、
末尾にプロセスがぶら下がって出力を追記し続ける状態を一級市民として扱えない
（`:terminal` は入れ子のエミュレータであって、バッファではない）。

## 中心命題

> **グリッドはドキュメントである。プロセスはその末尾に追記しているだけの存在にすぎない。**

この一文から、ユーザーが「譲れない」とした4本すべてが導かれる。設計上の判断に迷ったら、
毎回ここに戻る。

| 譲れない機能 | 命題からの導出 |
|---|---|
| モーダル操作 | ドキュメントなら、モーション・テキストオブジェクト・オペレータが当然に効く |
| マウス完全等価 | ドキュメントなら、ポインタで場所を指し、掴み、範囲を取れて当然 |
| 多重化・セッション永続 | ドキュメントは開いているウィンドウより長生きする。閉じても消えない |
| エディタ内蔵 | ファイルバッファとグリッドが同じ `Buffer` なら、エディタは追加機能ではなく**同じ実装の別入力元** |

4本目が特に重要で、これは「ターミナルにエディタも足す」という機能追加ではない。
**グリッドをドキュメント型にした結果、エディタがほぼ自動的に生えてくる**という順序である。
逆順（エディタを足す）で作ると必ず失敗する。

---

## 取るもの

**WezTerm から**

- `portable-pty` 相当の PTY 抽象（そのままクレートを使う。ConPTY を自作しない）
- GPU 描画による高リフレッシュレート・低レイテンシ
- **mux をサーバプロセスとして分離**する構成（永続性を後付けにしないための唯一の正解）
- リガチャ・フォントフォールバックの品質基準

**Neovim から**

- モードという概念そのもの
- `[count] operator [count] motion|textobject` の合成文法（機能数ではなく**掛け算**で強くなる設計）
- テキストオブジェクト
- レジスタ、マーク、マクロ、`:` コマンドライン
- 「エディタは操作されるプログラムである」という思想（＝外部から駆動できる）

## 捨てるもの（明示）

捨てる判断を先に固定する。ここが緩むと、この規模のプロジェクトは完成しない。

1. **Neovim プラグインエコシステムとの互換**
   Lua API も Vimscript も実装しない。treesitter/LSP は必要なら**自前で直接**統合する。
   互換レイヤを目指した瞬間、本体の設計自由度がゼロになる。

2. **vi 互換の細部**
   `:s` のフラグ完全一致、vi 由来の歴史的挙動、`'compatible'` 相当は追わない。
   「vim を知っていれば9割そのまま動く」までを目標にし、残り1割は**ターミナル固有の語彙に使う**。

3. **入れ子のターミナル**
   `:terminal` は存在しない。ペインが常にプロセスを持てる以上、入れ子は不要であり、
   入れ子を許すとモード所有権の裁定が破綻する。

4. **tmux キーバインド互換**
   prefix キー方式は採らない。多重化は本体の一部であり、別レイヤではない。

5. **v1 での組み込みスクリプト言語**
   設定は宣言的な TOML。ただし**外部から駆動するRPCの口（`tsg-mux` のソケット）を v1 から開ける**。
   スクリプト性はここから供給する。将来 Lua/WASM を足すときも、この口の上に乗るだけで
   本体設計を壊さない。「WezTerm の Lua に相当するもの」を最初から抱えると M0 に到達できない。

6. **マウスレポートの無条件パススルー**
   これが最大の争点。次節。

## 最大の設計衝突: 誰がマウスと Esc を所有するか

TUI アプリ（htop, lazygit, k9s, fzf, less …）は SGR 1006 でマウスレポートを有効化し、
生のマウスイベントを欲しがる。一方 tsumugi は、同じマウスで自分のモーダル層を駆動したい。
**両方は成立しない。**

既存の解は「Shift を押しながらなら端末側が取る」という修飾キー方式で、
これは「マウス完全等価」とは両立しない（常時修飾キーを押す操作を等価とは呼べない）。

Esc も同型の問題を持つ。Esc で Normal モードに入る設計にすると、
子プロセス側の vim ライクなアプリに Esc が一切届かなくなる。

### 採用する解: **alt-screen を所有権の境界にする**

| 子プロセスの状態 | マウス | Esc | 根拠 |
|---|---|---|---|
| **primary screen**（シェルのプロンプト＋スクロールバック） | **tsumugi が所有** | **tsumugi が所有** | ここは「ドキュメント」。追記されたログを読み・掴み・使う場所であり、子プロセスに生の座標は要らない |
| **alternate screen**（全画面 TUI） | **子プロセスへ委譲** | **子プロセスへ委譲** | ここは「アプリ」。htop の行をvimで選びたい人はいない。そのアプリのマウスが欲しい |

この規則の良さは、**観測可能で・状態が明示的で・ユーザーの直感と一致する**こと。
「今どっちが持っているか」は画面を見れば分かる（＝ステータス行に所有権インジケータを常時出す）。

**逃げ道を2つだけ用意する**（それ以上は増やさない）:

- `C-\` — 所有権を無視して強制的に Normal モードへ。alt-screen の内容もドキュメントとして掴める。
- `:pin mouse app|self` — 特定ペインの所有権を固定する。行儀の悪いアプリ用の手動オーバーライド。

**そして、この衝突の大半はエディタ内蔵によって消える。**
最も頻繁に alt-screen を占有するアプリは vim である。tsumugi ではそれが内蔵エディタになり、
同じモーダルエンジン・同じ所有権の下で動く。残る衝突相手は htop / lazygit / k9s 程度で、
それらは「アプリにマウスを渡す」で全く困らない。

## 「これさえあれば」の成立条件

以下がすべて満たされたとき、この道具は他を要らなくする。

1. `nvim` を別途インストールする理由が無い（内蔵エディタが同じ操作体系で足りる）
2. `tmux` を起動する理由が無い（永続セッションが本体機能）
3. スクロールバックからのコピペで**マウスを持ち替える必要が無い**（キーでもマウスでも同じ道具箱）
4. 日本語入力・CJK 幅・IME が**壊れない**（後述。既存 Rust 製ターミナルの弱点であり差別化点）
5. ログの中のパス・URL・エラー行が「掴んで次のコマンドに渡せる」オブジェクトとして振る舞う

## 非目標

- Web ターミナル / SSH クライアント機能の内蔵（v1 では ssh は普通に子プロセスとして動かす）
- ペイン内での画像プロトコル完全対応（sixel/kitty graphics は M5 以降の検討）
- AI エージェント統合（設計は妨げない。`tsg-mux` の RPC で外から可能な形にしておくに留める）
- 既存ターミナルからの設定移行ツール
